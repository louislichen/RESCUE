# 关键路径核查与第二轮系统优化（2026-10-17）

本轮由用户明确要求：检查关键路径阻塞、模块耗时，并在原生SD及SpecExtend
检索对照下进行系统优化。先做训练侧诊断，再实现执行优化与长度校准，最后
在参数冻结后重测已有验证集。旧结果、冻结源码和CSGB归档保持不变。

后续按用户要求深入检查权重、数据流与执行组织，另见
[THROUGHPUT_ANALYSIS](../../docs/THROUGHPUT_ANALYSIS.md)。其中的新候选仅经过源码
与CPU记录分析，尚未实现或新增GPU验证，不改变本报告原始测量范围。

## 关键路径及计时方法

本地默认串行路径为：

```
已提交T/S注意力 → ReadState → M3独立特征 → M1选择
  → M3依赖R的特征/长度评分 → 工作KV整理 → M2静态映射
  → 草稿逐token forward及动态门控 → 完整Target验证
  → 提交/必要Draft缓存补算/回滚 → 下一轮
```

TCP/异步路径可以将M3尾部与M2及首个Draft token重叠；同GPU本地默认仍为串行。
本轮不把异步线程视为无成本，也没有新增完整边云模型部署。

`rescue.profiling` 用CPU单调时钟和CUDA event记录嵌套区间，在请求结束后统一
同步读取event，不在每个阶段插入GPU全局同步。CUDA timeline含区间内主机发射
导致的空闲，不等于kernel忙碌时间。CPU与GPU列不能相加；父子区间也不能相加。
Target `_forward` 区间不包括后续lm_head和argmax，而整请求计时包含它们。

第一次诊断位于 `out_profile_before_20261017`，训练1500/1501，输出上限64。
此版本还对每层空门控调用打了细粒度event，扰动较大，只用于定位和调用计数。
正式优化矩阵的 `diagnostic_profiles.json` 关闭这类微区间，并保留legacy/optimized
在同一分析器下的诊断。所有诊断请求排除在正式吞吐表之外。

## 执行修改

1. **直接GQA读取。** Draft SDPA直接读取原生KV头，避免每层显式展开复制K/V；
   最后一层full-key注意力探针改为分组矩阵乘法。未减少历史位置或改变选取预算。
2. **直接工作KV gather。** `index_select(..., out=工作buffer)`去掉中间结果和copy；
   位置范围/顺序检查合并成一个设备标量判定。保留私有工作KV与完整原生KV隔离。
3. **静态门控分解。** 首层门控仿射变换中，Teacher映射、native特征、注意力与
   位置、cosine项每轮算一次；每个query只重算query项再求非线性与最终门控。
   没有把query门控冻结成每轮常量。
4. **必要补算只更新状态。** 全部草稿接受后，非末轮仍补算最后Draft输入以提交
   各层KV和注意力，但跳过随即丢弃的final norm/lm_head。
5. **避免未使用的工作。** 固定长度/非读取保持路径延后完整A·V读出和V转FP32，
   只在实际需要时计算；跳过没有注入的层的空门控调用。沿用工作集且历史增长时，
   不再构造、排序不会使用的补选池，位置输出及预算契约保持一致。

公共GQA、gather和补算优化也给原生SD、SpecExtend检索路径使用。`optimized_execution`
开关保留legacy执行，用于同次随机化请求的对照；数学等价不代表Draft浮点逐位相同。
最终生成仍必须匹配独立FP32 eager完整Target参考。

## 长度问题与训练边界

旧长度预测器权重沿用注入前训练；其误差与注入/新执行成本之间的失配需要实测，
不能仅凭看到k较小就断定根因。当前系统把成本视为加性近似，第一token的GPU排队
也可能污染简单主机计时，因此单独保留真实cost样本及分段诊断。

本轮明确分开三个优化条件：

- `optimized_oldrisk`：只改执行，保留旧预测器与旧成本；
- `optimized_fixed`：同一选择与注入，固定长度只在训练侧挑选；
- `optimized_calibrated`：重新测实际成本，并对注入条件下的接受风险做两参数校准。

校准只拟合logit整体缩放及继续接受类别的偏置，用带右删失的三类风险似然，
按文档平衡样本，L2系数0.01。基础预测网络、mapper和大/小模型均不重训。
校准可折入最后线性层权重，无额外线上网络层。校准JSON绑定原风险checkpoint哈希，
本地及TCP服务均可显式加载；默认不悄悄替换任何权重。

训练前4篇只做风险/成本校准，后4篇只选固定长度并作训练侧策略对照；验证集
不参与校准或选参。三个基线及完整固定方案均比较k={1,2,4,8,12}后锁定。
完整固定方案属于长度模块消融，不能把它写成三个模块联合均已成功。

## 为什么相对基线仍慢

### 每轮固定成本与产出不匹配

| 条件 | 实际输出token/轮 | Decode平均毫秒/轮 |
|---|---:|---:|
| 原生SD | 3.070 | 82.18 |
| legacy | 2.400 | 78.41 |
| 只改执行 | 2.400 | 74.75 |
| 固定4消融 | 3.046 | 94.34 |
| 校准长度 | 2.977 | 97.27 |

原风险策略虽使单轮更短，但每轮只产出2.4个token，未能抵消更多轮次。固定4后
验证轮数接近原生（260对258），Draft forward也接近（1102对1104），而完整方案
每轮时间仍更长：额外的选择、注意力观测、工作缓存和注入需要真实收益来偿还。
接受率54.29%与原生53.98%接近，不能据此认定当前组合在该数据上改善了接受质量。
这个对照改变的是整套上下文/注入组合，不能单独判定mapper或选择器无效。

### 调度与模块开销确实存在，参数少不代表免费

为避免首个诊断请求的冷启动影响，下面仅描述训练1501的第二篇诊断，非正式
吞吐结论。其动态策略两种执行均12轮、轨迹相同。CUDA timeline平均每轮：

| 区间 | legacy ms/轮 | optimized ms/轮 |
|---|---:|---:|
| 状态构造 | 0.314 | 0.145 |
| M1选择（含摊销刷新） | 2.173 | 1.639 |
| 工作KV整理 | 1.061 | 0.782 |
| M2静态准备 | 2.118 | 2.343 |
| M3独立特征 | 0.576 | 0.578 |
| M3依赖R的特征 | 0.590 | 0.737 |
| M3评分 | 0.590 | 0.592 |
| Draft forward合计，含动态注入 | 40.310 | 37.136 |
| Target主体验证 | 26.250 | 26.231 |

静态门控分解把一部分工作移到每轮准备，未使所有子阶段都变快。延后的A·V
计算也可能转移到M3特征阶段，应以完整请求及合计路径判断，而不是单项计时。
当前本地请求没有TCP等待；M1、M2准备与M3仍占串行关键路径。Draft与验证之间
有真实数据依赖，不能将它们任意并行后就认定成本全被隐藏。

### 简单长度校准尚未解决策略问题

两参数校准在4篇训练文档的加权风险NLL由0.4382降为0.3932，**这是拟合损失**。
校准后验证集上限分布为k=2/4/8分别60/170/34轮，另有2轮末尾k=1；原风险策略
为286/36/0轮及8轮k=1。更长草稿使轮数从330降到266，但Draft forward从890
增至1140，最终没有稳定速度收益。不能将训练似然下降或验证轮数下降等同于净加速。

因此，当前得到的是**执行优化的正结果**，同时明确了剩余的组合/长度策略问题。
固定4控制也没有超过基线，继续只微调长度不能保证解决问题；后续需要同条件
固定长度下逐项验证选择/内容注入的净收益，以及更充分的注入条件下风险/成本
校准。本轮没有重训mapper、完成这种新模块消融，或证明三个论文模块均有独立贡献。

## 正确性、可复现性和实际使用

25项CPU检查通过。记录审计重算29份冻结源码哈希、请求矩阵、预算、回滚前缀、
必要补算、固定长度训练选择、风险校准及统计量；128验证+92选择+4风险采集请求
共224个保存输出全部一致。208个投机请求UUID唯一；28个风险frame的标签与右
删失另与原始接受轨迹核对通过。成本校准的6请求及单独诊断均在执行时检查Target
一致性，不并入正式吞吐表。记录审计不等于再次重跑GPU。

普通推理默认使用优化后的执行；下列参数显式选择本次成本与风险校准，不将未证实
有效的校准设为隐式默认：

```bash
python -m rescue --prompt-file prompt.txt --verify \
  --cost exp/system_validation/out_optimization_v1_20261017/cost.json \
  --risk-calibration exp/system_validation/out_optimization_v1_20261017/risk_calibration.json
```

固定长度消融可用 `--length-policy fixed --fixed-k 4`；`--legacy-execution`保留旧执行。
TCP长度服务也支持相同的 `--risk-calibration`，但本轮吞吐矩阵没有新增RPC计时。
