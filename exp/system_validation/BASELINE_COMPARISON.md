# 原生 SD 与 SpecExtend 检索机制的匹配对照

这轮补充对照回答：完整 RESCUE 是否比未干预的原生 SD 更快，以及相对
SpecExtend 的跨模型注意力检索机制表现如何。旧系统报告中的 +28.93% 是相对
已有三个研究模块的旧 pipeline，不能当成相对这两个基线的提升。

后续关键路径核查、执行优化和基线同等优化后的新结果见
[SYSTEM_OPTIMIZATION](SYSTEM_OPTIMIZATION.md)。本页保留此前独立运行的原始结果，
不可用跨运行TPS的比值归因工程收益。

## 对照范围

- 同一 H100、Qwen2-7B/1.5B、Target eager FP32 / Draft BF16，关闭 TF32。
- 所有 SD 模式共用预分配原生 KV、Draft SDPA、完整 Target 验证、提交与拒绝回滚。
- **原生 SD** 保留完整 Draft KV，固定生成长度；不采集 T/S 注意力、不构造工作
  KV、不执行选择器、mapper 或长度预测器。另保留惯用固定 k=4。
- **SpecExtend 检索移植**：chunk32，按最后层 Target 的头平均注意力计算 chunk
  均值，保留最高的历史 chunk 与最新 chunk，每四轮验证刷新，首次使用最近 chunk。
  最新已提交 query 的注意力在下一轮因果使用；不额外调用 Target。
  新增 frontier 时按照仓库归档实现淘汰最旧保留 chunk，维持 chunk 数上限。
  同时测试 Top16（最多512历史token）及 Top32（最多1024），无 mapper、固定长度。
- **完整 RESCUE** 沿用上一轮 coverage 配置与训练集校准成本，不重训或验证集调参。
- **Target AR** 在同一矩阵中重新计时，采用完整原生上下文，不运行 Draft。

这不是原版 SpecExtend 完整系统复现。本机仅有 Qwen2 基础模型；仓库原版是
Llama/Vicuna 树解码，并包含 Flash Prefill 与 Hybrid Tree Attention。本轮只将其
检索机制移植到相同 Qwen2 线性 SD 骨架，不能据此宣称超过原版完整系统。
同预算指最大历史 token 数，SpecExtend 的末尾不足一个 chunk 时实际保留数会更少，
不把最大512误写成每轮恰好512。Target 始终使用完整历史。

## 预先固定的协议

训练文档1500/1501，每个基线家族分别比较 k={1,2,4,8,12}，两次计时重复，
共60次训练侧请求。按训练侧总输出/总完整请求时间选定各家族 k，写入文件后
才开始验证计时。已有8篇验证文档1554–1561，每条件两次计时重复、输出上限64。
六条件共96次验证请求；每文档每重复随机化条件顺序。预热、模型加载与独立
输出参考不计入请求时间，缓存分配、prefill、算法开销、验证和清理均计入。

TPS表使用总实际输出/总时间。配对变化先取每篇文档两次TPS的中位数，再计算
RESCUE相对基线的百分比，按文档 bootstrap5000次，seed42，经验95%区间。
训练样本很少，验证集已在旧研究中使用；这是系统补充对照，不是独立长文本确认实验。

## 已完成结果

三个基线家族均在训练侧选中 k=4。因此 `native` 与预先安排的 `native_k4` 设置
相同，后者只作为额外计时复核，不是第二种算法或独立文档样本。两组逐轮轨迹一致。

| 条件 | 草稿长度 | Decode TPS | 整请求 TPS | 接受率 | 验证轮数 |
|---|---|---:|---:|---:|---:|
| 原生 SD，全上下文 | 固定4 | 34.818 | 24.436 | 53.98% | 258 |
| 原生固定4复核 | 固定4 | 34.830 | 24.439 | 53.98% | 258 |
| SpecExtend检索移植 Top16 / ≤512历史token | 固定4 | 34.147 | 24.034 | 56.67% | 250 |
| SpecExtend检索移植 Top32 / ≤1024历史token | 固定4 | 34.085 | 24.043 | 56.58% | 252 |
| 完整 RESCUE | 风险长度策略 | 29.913 | 21.900 | 65.64% | 330 |
| Target AR | — | 47.362 | 30.793 | — | — |

每条件16请求、792个实际输出 token。下面百分比按文档配对计算，与上表池化TPS
的比值不同；区间只反映这8篇文档及固定训练权重/长度选择，不含训练选择不确定性。

| RESCUE 相对基线 | 配对 Decode TPS 变化 [95% CI] | 配对整请求 TPS 变化 [95% CI] |
|---|---:|---:|
| 原生 SD | -13.32% [-19.38,-6.48] | -10.23% [-14.61,-5.55] |
| SpecExtend检索 Top16 | -11.23% [-18.18,-3.41] | -8.43% [-12.92,-3.49] |
| SpecExtend检索 Top32 | -12.45% [-16.57,-9.05] | -8.63% [-11.41,-6.04] |
| Target AR | -35.13% [-38.63,-31.09] | -27.54% [-31.63,-22.90] |

因此，**当前完整系统尚未获得相对原生 SD 或同骨架 SpecExtend 检索的净加速**。
旧报告的正收益只成立于相对旧干预 pipeline；这两种结论应同时保留。
本轮不支持任何超过原版完整 SpecExtend 的表述，也不能外推到8K/16K。

## 从保存轨迹能看出什么

完整 RESCUE 的330轮中，286轮长度上限为2、36轮为4、8轮为1；包括剩余输出
长度的末轮截断。原生SD的258轮中，252轮上限为4，其余为末轮截断。
两者分别提出716/1004个 token，接受470/542个，平均每轮接受1.424/2.101个。
较短草稿的条件下，更高接受率没有转化成更少验证轮数。

完整方案实际 Draft forward 为890，原生为1104；它减少了 Draft forward，仍然更慢。
这说明需要联合看验证次数及控制/工作缓存/注入成本，不能仅用接受率或草稿计算量
作为系统收益证据。这些总计数没有分离各模块成本，不能据此断定损失全由长度模块造成。
下一步的可归因检查应锁定长度再逐项加入选择与注入，并测完整阶段时间；本轮没有
执行这组新消融或重新训练长度预测器。

SpecExtend Top16/Top32 每轮历史工作集均值为496.416/997.135 token，符合末尾
不足一块时小于预算上限的协议；均为66次实际检索刷新。完整方案为严格512历史
位置、90次覆盖重选。原生SD没有工作集gather、Target/Draft注意力探针或mapper。

完整方案与上一轮coverage的16/16组长度/提出/接受轨迹一致。这次通过同批随机化
重新计时比较，不将两轮绝对TPS差异解释为算法变化。
