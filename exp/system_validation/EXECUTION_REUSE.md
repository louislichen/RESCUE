# 按需观测、门控复用与工作KV组织优化（2026-10-17）

按用户要求落实[前一轮实现分析](../../docs/THROUGHPUT_ANALYSIS.md)中的优化。
先保持既有选择、mapper和长度权重，逐项修改执行；另提供训练侧可选的注入计算
路由。原模型、实验来源、旧冻结源码与报告保持不变。

## 本轮实现

1. **按需完整历史注意力。** 每个Draft forward只保存最后层RoPE后的Q，验证后
   依据实际接受长度选择Q，先将原生KV裁剪到对应前缀，再计算下一轮唯一所需的
   完整键注意力。全部接受时保留必要缓存补算；末轮不做无用的下一轮探针。
   此版本M3不消费草稿中间的新注意力，所以没有删除当前策略必需的输入。
2. **静态内容仿射memo。** 已提交位置的Teacher/native内容、cosine与首层门控
   仿射项只在该位置首次使用时计算；每轮只更新注意力/位置项，每个query继续
   动态计算query编码和门控。权重子矩阵提前打包，减少反复拼接与无用特征gather。
3. **跨层批量KV。** 原生及工作K/V采用具有逐层view的连续存储，`packed`路径
   用两次跨层`index_select`替代逐层调用，完整原生KV语义与绝对RoPE保持不变。
4. **可选增量工作KV。** `incremental`维护token到物理slot映射，小幅工作集变化
   只更新新增位置；更新前先恢复上一query注入过的原生V，避免错误累积。较大变化、
   缓存形状改变或新请求会重建；拒绝尾部不进入已提交位置memo。
5. **真实计算路由。** 可以指定注入层、位置数和强度，未选层不分配对应内容memo、
   不执行query门控。`joint`排名可复用M1的T/S联合注意力候选分数；门控的Teacher
   注意力输入仍沿用训练定义。它只统一联合注意力排名，**不是传递了完整边际覆盖
   增益，也不是已训练的逐query动态层选择器**。

前三类配置都保留显式对照开关。物理slot顺序与FP32仿射求和组织可能改变Draft
浮点结果，不能仅凭公式等价保证全部轨迹相同；完整Target验证始终保留。

## 协议

输出目录：`out_reuse_v1_20261017`。Qwen2-7B/1.5B、H100、Target eager FP32/
Draft BF16、TF32关闭、相同现有数据与64输出上限。长度风险网络与cost沿用冻结
权重/配置，本轮不重训mapper/风险网络，避免把执行收益与训练变化混合。

- 执行筛选：训练1500/1501，两次重复；比较上一轮执行、按需探针、再加仿射memo、
  再加packed KV、incremental KV。由训练整请求TPS选定affine/packed/incremental。
- 路由筛选：前8篇训练文档，9个固定路由、每篇一次计时；比较四层/两层/一层、
  128/64位置、0.5/0.25强度、Teacher/联合排名与关闭注入。保留最优非零及零允许
  选择；这些是静态层/token预算校准，不是重新学习mapper内部权重。
- 验证：已有1554–1561八篇，两次计时重复，各条件随机顺序。固定长度4沿用此前
  训练选定值，不用本次验证结果挑k。
- 同时比较上一轮/新执行的风险长度与固定4、训练选定非零路由、coverage开关注入、
  Teacher token选择开关注入，以及原生SD、SpecExtend检索Top16/32和Target AR。
- 原生与检索基线使用相同原生存储组织和训练选定的工作KV实现；原生SD继续关闭
  所有干预探针和mapper。SpecExtend仍为同Qwen2骨架检索移植，不含原版树/Flash引擎。

每条件先用训练文档预热。模型加载、参考、预热与参数选择不计入验证请求时间；
缓冲区建立、两模型prefill、控制计算、mapper、Draft、验证与清理计入。统计单位
为文档，TPS表用总输出/总时间；配对区间先取同文档两次TPS中位数，再算相对变化，
bootstrap5000次、seed42。条件数量较多、验证集复用、只一个模型对，不能解释为
独立确认、长上下文泛化或单独模块的普遍有效性结论。

## 使用与复现

普通推理默认开启按需探针和静态仿射memo，工作KV默认`packed`；可选项：

```bash
python -m rescue --prompt-file prompt.txt --verify --working-mode incremental
python -m rescue --prompt-file prompt.txt --verify \
  --working-mode layerwise --eager-probes --round-gate-affine
python -m rescue --prompt-file prompt.txt --verify \
  --injection-layers 26 27 --inject-tokens 64 --injection-strength 0.5 \
  --injection-rule joint
```

最后一条只是配置示例，不表示该配置已经最优。全局零强度/零位置/空层集合会
跳过注入计算；不能把关闭模块后的速度表述成完整三个模块的成功。

```bash
PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -v
PYTHONDONTWRITEBYTECODE=1 python -m rescue.reuse_benchmark \
  --output exp/system_validation/new_reuse_run
OMP_NUM_THREADS=4 python -m rescue.reuse_audit exp/system_validation/new_reuse_run
```

输出保留协议、执行源码、原始请求、数据与权重哈希、训练选择、模式配置和完整
Target参考。执行计数区分逻辑工作缓存更新、完整gather、实际读取位置层数和旧V
恢复次数；不会将增量维护伪装为没有缓存工作。

## 训练侧选择与增量缓存计数

20次执行筛选请求全部匹配Target。`packed`整请求TPS为22.907，`incremental`
为22.902，因此锁定前者。差异很小，不能据两篇训练文档认定批量方案在所有长度
上优于增量方案。两者的新执行特性相同，仅工作KV组织方式不同。

相同四个训练请求中，上一轮执行、按需探针、再加仿射memo的整请求TPS分别为
22.737、22.770、22.818。计数上，decode完整键探针从188次降到68次；静态门控
内容仿射从36,864位置层降到7,616位置层。`packed`完整gather仍读取1,032,192
位置层，只把逐层读取组织成两次跨层调用；不能把它表述为减少了KV字节数。

增量方案实际读取240,072位置层，较packed少76.74%；56次增量绑定，并恢复
28,672位置层的旧工作V修正，但没有获得额外整请求加速。它包含CPU位置映射、
恢复与scatter成本；这些计数不能单独归因出各项耗时。该路径保留为可选项，
没有据此声称长上下文无效。物理顺序改变也会改变部分Draft数值与选择轨迹。

72次路由筛选请求全部匹配Target。九个候选的整请求TPS如下；同一训练文档各
条件只有一次计时，选择结果需通过后续固定配置验证，不能作为独立泛化结论。

这里固定4是长度消融，不是重新设计的动态长度模块。

### 纯执行保持了什么，减少了什么

原风险长度、固定4分别16/16组`cap/proposed/accepted`轨迹与上一轮执行一致，
原生KV与Target完整验证语义保持。CPU逐轮快照测试另核对了延后探针的注意力
完全相等；GPU轨迹/输出核查并不等于逐张量、所有精度的位级证明。

| 固定策略 | decode完整键探针，旧→新 | 静态门控内容仿射位置层，旧→新 |
|---|---:|---:|
| 原风险长度 | 890→314（−64.72%） | 168,960→33,312（−80.28%） |
| 固定4 | 1102→244（−77.86%） | 133,120→31,136（−76.61%） |

完整工作KV读取位置数在packed下不减少。绑定仍是330/260轮，代码将每轮56个
逐层K/V gather调用改成2个跨层调用；这不是GPU profiler测得的kernel数量。
这些大幅调用/位置计数下降只对应约1%的整请求收益，不能换算成等比例加速。
新旧风险权重、cost、四层注入和位置/长度策略相同，不将路由改变混入纯执行收益。

### 固定长度消融说明了什么

在coverage选择、固定4、相同执行下，四层注入使接受/提出从534/1026提升到
544/1002（52.05%→54.29%），验证轮数仅262→260，整请求反而慢3.46%。这说明
**当前配置的接受收益不足以回收实际总成本**，不是单凭mapper参数量大小即可判断。
开关注入也会改变轨迹，因此该比较是净系统效应，不是mapper纯算子耗时分摊。

最后一层×64把验证轮数降到258，少于无注入的262，但整请求TPS相对无注入的
区间仍跨零，decode则略慢。它支持“少做注入比现有四层方案更划算”，尚不支持
“保留非零注入已获得净加速”。Teacher选择下四层注入也没有速度收益，说明问题
不只是coverage与Teacher注入排名不一致。它不推翻旧协议的接受正信号，也不能
据此断定所有层配对或内容补充必然无效。

本轮固定4是诊断消融，未获得新的动态长度正结果；M3依旧不直接输入当前注入
门控、残差或路由预算。四层/轻量mapper均沿用旧训练状态分布，本轮没有解决
联合rollout的监督与分布适配。后续应把接受收益、计算预算和真实增量耗时共同
纳入注入学习，再在该配置下训练长度决策；不能把工程优化当成这些训练已经完成。

## 核验与证据边界

31项CPU测试通过，包含packed对齐、旧V恢复、拒绝尾部、物理映射、重复请求、
逐轮延后探针对齐、静态门控等价、真实小型Qwen门控与空路由跳过计算。
`reuse_audit`检查32份冻结源码、数据矩阵、训练/验证分离、路由选择重算、
缓存/仿射/探针计数、接受与必要补算、EOS/输出上限及全部配对统计，均通过。
保存的192验证＋20执行选参＋72路由选参共284输出全部匹配Target，268个投机
请求UUID唯一；16个Target AR计时请求不使用投机UUID。
