# 首轮流水线执行验证（2026-10-17）

已实现版本化的异步长度通道，并缓存静态 V 映射。模块1先给出 R，模块3的
R 相关决策与模块2准备和首个正常 Draft forward 重叠；在第二个 token 开始前
必须取得长度。迟到就等待，不默默增加草稿长度，不丢弃版本不匹配的消息校验。

**这是本地单 H100 的调度验证。10 ms 是人工服务/分发延迟，不是真实边云网络实测。**
现有模块3依赖 R，因此还不是模块1/3的全量独立并行；也没有重训注入后的长度预测器。

## 结果

TPS 按该模式总实际输出/总实际耗时计算，是小规模描述统计，没有推断性置信区间。

| 延迟条件 | 执行方式 | Decode TPS | 含 prefill 总 TPS |
|---|---|---:|---:|
| 0 ms | 原实现串行 | 22.868 | 16.415 |
| 0 ms | 新循环＋原始注入，串行长度 | 24.677 | 17.313 |
| 0 ms | 缓存注入，串行长度 | 25.349 | 17.665 |
| 0 ms | 缓存注入，异步长度 | 24.590 | 17.295 |
| 模拟10 ms | 原实现串行（没有添加延迟，仅锚点） | 22.869 | 16.380 |
| 模拟10 ms | 新循环＋原始注入，串行长度 | 22.394 | 16.130 |
| 模拟10 ms | 缓存注入，串行长度 | 22.942 | 16.421 |
| 模拟10 ms | 缓存注入，异步长度 | 24.677 | 17.295 |

同一新循环内，0 ms时缓存注入相对原始注入提高2.72% decode TPS。
0 ms时异步相对串行缓存下降2.99%，总TPS下降2.09%；
模拟10 ms时异步相对串行缓存提高7.56%，总TPS提高5.32%。
这些对照不等于超过 Target AR，或整篇论文架构具有加速效果。

原实现与新循环还存在 capture、同步与 policy spent 输入差别；每个延迟条件六组
文档/重复中，只有三组的原实现接受轨迹与新循环一致。不能把原实现→新循环的全部
变化归因于缓存或流水线。两个新串行模式与异步模式之间才是受控的执行对照。

## 对执行方案的含义

这轮支持先保留两种执行方式：低延迟本地环境用串行缓存；存在可覆盖的分发等待时
可用异步缓存。当前单卡异步即使不等待结果仍更慢，说明“消息及时到达”不足以
证明零总开销；与线程调度/GPU资源争用相容，具体占比仍需 profiler 分离。

真实边云需要把 R/内容包与长度包分开发送，不能为了等待长度而延迟内容包。
以消息实际到达时间判断是否满足首个 token 的截止点；同时计入快照输入传输、
teacher内容字节量、RPC、设备资源、验证返回和整请求耗时。
若要让 M1/M3 完全并行，需要拆分 R 无关特征与 R 相关决策，或训练不依赖 R 的控制器。
本次没有静默替换原预测器或声称独立并行已经实现。
