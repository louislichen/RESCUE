## 1. 先定位损失发生在哪个层面

固定k=4，16个请求均输出792 token：

| 指标 | 同等优化原生SD | 选择+注入、固定4 |
|---|---:|---:|
| 验证轮数 | 258 | 260 |
| Draft forward数 | 1104 | 1102 |
| Decode总秒数 | 21.202 | 24.529 |
| Prefill总秒数 | 9.670 | 9.737 |
| 平均Decode ms/轮 | 82.18 | 94.34 |

差距主要发生在decode，而非prefill。按恒等式分解：

```
额外decode时间
  = 额外轮数 × 原生平均轮耗时
  + 本方案轮数 × 两者平均轮耗时之差
  = 0.164秒 + 3.163秒 = 3.327秒
```

约95%的该项差额在账面上来自更高的平均轮成本。**这是聚合时间的代数分解，
不是把95%损失归因于某个组件，也不是控制了所有query、末轮和缓存状态的因果消融。**
不过固定长度、轮数和Draft调用数接近，确实排除了“只要把长度改成4就会解决”的判断。

在保持平均轮成本和其它条件不变的粗算下，本方案每轮需要多产出约15.7%的最终
token才追平原生decode速度；或者需要相应降低每轮成本。这不是对新参数效果的预测。

## 2. 权重有两种问题：计算组织，以及训练条件

### Mapper参数量小，但调用粒度很碎

当前mapper checkpoint为700,804个参数、FP32约2.67MiB，四套独立层网络，rank64。
Teacher来源层为24/26/26/27，Student注入24/25/26/27（均零起始）。

Teacher投影、native编码与残差方向已经按已提交位置缓存，**不是每生成一个token
都重跑完整Teacher-V mapper**。剩余重复主要是每个注入层的query编码、门控计算、
V修正与索引写回。固定4矩阵有1102次Draft forward，对应4408次token/层门控调用。
虽然每个小网络算术量不大，仍会触发多次LayerNorm、Linear、激活、类型转换与scatter。
精确kernel忙碌/发射时间占比尚未测量，不能将它们全部称为纯kernel-launch开销。

当前sigmoid门控只控制修正数值，不是计算路由：门控小仍要完成前面的计算，
默认每轮选128个位置并在四层全部执行。把全局强度0.5调小不会自动省掉这些成本。

可优先尝试、但尚未实现：

- 把每轮重新拼接的静态门控权重提前打包；将不随query/轮次改变的内容仿射项
  放入位置memo，每轮只加注意力与相对位置项。现版只将其从逐query移到逐轮。
- 在准备阶段将四层同形状的静态网络组织为批量运算；当前query依赖层序推进，
  不能声称四层动态query门控也可以任意并行。
- 融合门控后的点乘、类型转换和V写回，减少小算子及中间结果。
- 引入便宜的每轮层/token预算选择，使“不注入”真正跳过计算；不能先跑完完整
  mapper/门控再判断门控很小，就把它算作计算稀疏。逐层GPU转Python的硬分支也可能
  引入额外同步，路由实现本身必须计时。

BF16 mapper、rank缩小、共享Teacher编码器是后续候选，需要重新验证效果。
当前FP32 Teacher-V先量化BF16再转FP32，目的是匹配训练来源；不能无依据删除这一步。
鉴于权重本身只有2.67MiB，不能保证只缩小权重存储就能解决总吞吐差距。

### Mapper训练与当前组合存在可核对的分布变化

[原始训练](../exp/selective_kv/run.py)使用Teacher单独的token注意力筛选、固定512
工作集，校准出的全局强度0.5也是在这套配置上选的。采集状态来自完整原生Student
沿Teacher轨迹推进，然后对缓存状态做单query干预训练。目标为输出KL、Teacher
argmax CE与残差惩罚；不是当前三模块滚动执行的完整请求吞吐目标。

现在则是T/S联合覆盖选择，随后连续草稿中逐query门控，生成的已提交Student KV
又会受先前注入影响。已有checkpoint和0.5强度没有在新选择/滚动状态下重新训练。
这是代码中确认的条件变化；它是否解释了收益损失仍需对照，不能写成已证明因果。

优先让权重适应实际组合：在训练集真实选择+注入rollout上重新校准层强度、注入
预算和风险模型，再考虑共享/低秩压缩。旧独立实验的正接受信号不保证迁移到新组合。

## 3. 三个模块目前没有共享同一个“值得补充”定义

### 选择与注入对token的排序不一致

[M1](../rescue/selection.py)按T/S注意力及各自V内容的覆盖增益选R，Student权重默认1。
但[M2](../rescue/injection.py)进入R后又仅按Teacher注意力重新排序，取128个位置注入。
M1挑出的高Student关注/高新增覆盖位置，不一定得到M2内容补充。

此外，M1内容覆盖只看T/S最后层V，M2实际Teacher内容来自24/26/27层，当前R不显式
优化这些来源层的可补充内容。各自都是可用代理，但不能默认它们串接后目标一致。

候选改法：M1输出R时同时传递边际覆盖、T/S读取差异等分数，M2用“重要性、缺失
代理、预计内容修正收益和成本”决定注入位置，而非再次只做Teacher Top-K。Teacher/
Student权重λ、各层强度α和注入预算需要在相同组合上调节，不能只靠默认λ=1、α=0.5。
这些代理仍需验证，注意力差异本身不是已经证明的知识缺失或接受率因果来源。

### 长度模块不直接看到当前轮注入结果

[M3特征](../rescue/features.py)的读取保持误差使用原生V，与M1覆盖目标不同；当前
轮的mapper残差、注入位置/层预算和query门控不在输入中。串行路径甚至在
`injector.bind`之前就算完长度；异步路径虽可与首token重叠，也仍使用原始边界特征，
不等于已经实现“注入后再确认长度”。

两参数校准只能缩放/偏移已有风险logits，不能凭空补出这些特征，也不是在联合系统上
重训了预测器。现有仅4篇28轮校准，训练似然下降不能证明泛化或吞吐提升。

候选改法：保留低成本的边界长度预算；在首个正常Draft token后，用已产生的实际
门控、修正幅度或更便宜的注入收益摘要确认是否延长。新增特征/收益摘要应被复用，
避免为了判断注入是否有用而额外重跑Teacher或整套Student。

### 成本拟合并没有出现明显的整体失准

以保存的真实草稿长度与真实必要补算次数回算：

| 条件 | 预测decode秒数 | 实测decode秒数 | 请求平均绝对百分比误差 |
|---|---:|---:|---:|
| 优化执行、原风险 | 24.246 | 24.669 | 1.82% |
| 固定4 | 24.645 | 24.529 | 0.49% |
| 两参数风险校准 | 25.414 | 25.875 | 1.94% |

这不支持“总成本估计错了很多”这一解释。但回算使用真实已发生长度/补算次数，
排除了风险预测误差，不能验证未选动作的成本排序或期望接受量。应优先检查联合
系统的收益预测与特征，保留细化刷新轮/普通轮、不同注入预算成本的必要性。

## 4. 有两项明确的组织方式候选

### 完整历史注意力探针可从逐token改为按需一次

[DraftAttention](../rescue/attention.py)每个Draft forward都计算最后层Q对完整原生K的
softmax；[engine](../rescue/engine.py)验证后却只取`probes[count]`，或者全部接受时
使用必要补算的那条。当前M3没有使用草稿内每一步的这些新探针。

因此可保存各步的末层RoPE后Q，验证得出count并crop至已提交前缀后，再用选中的
Q和对应原生K计算唯一需要的注意力。对于拒绝轮，该Q原先可见长度正好就是
`n+count+1`；全部接受轮使用必要补算的Q。末轮无需构造下一轮快照。

按保存轨迹估算，仅decode探针调用可为：

| 条件 | 当前 | 按需计算候选 |
|---|---:|---:|
| 原风险长度 | 890 | 314 |
| 固定4 | 1102 | 244 |
| 校准长度 | 1140 | 250 |

这是调用数估算，**不是64.7%–78.1%的整系统加速**。需要实际实现后验证Q/K时序、
异常回滚、数值、显存生命周期和异步依赖；若未来M3改为使用草稿内实时注意力，
则需重新评估哪些探针不可省。

### 工作KV可以区分刷新与增量维护

当前`WorkingCache.bind`每轮gather全部28层，即使昂贵覆盖重选只在每四轮发生。
固定4矩阵执行7280层次gather；原风险长度为9240层次。对未刷新轮，当前carry逻辑
通常只引入本轮新增的强制recent位置，并从旧集合淘汰相同数量的位置。

候选改法：维护token到物理slot的索引，只更新新增/替换位置；刷新轮才整批整理。
需要恢复已退出注入集合但仍在工作集中的旧V，避免携带上一query的修正；还要保持
绝对RoPE位置、已提交原生KV与拒绝回滚。注意力物理slot顺序改变也可能改变浮点
归约顺序，应重新核对Target输出。这里没有测量工作集重合率或该候选的性能。

## 5. 为什么“缩短KV”在当前输入上可能省得不多

本机Student配置：28层、hidden1536、intermediate8960、12个Q头、2个KV头、BF16。
其Q/K/V/O与MLP权重约2.620GB，lm_head约0.467GB（与词嵌入共享存储）。
一次token forward对应的大矩阵权重操作数体量约3.087GB；相比之下，按每个KV
元素只读一次粗算，全28层K+V在N=1352时约38.8MB，N=512时约14.7MB。

以上是由shape计算的**逻辑操作数体量，不是实测DRAM流量、实际带宽或耗时比例**。
缓存、算子实现、激活和权重复用会改变物理访问；需要kernel profiling才能确认瓶颈。
但它提示：在约1–2K时，只省KV注意力访问，未必能覆盖新增控制网络和索引操作。
不能据此否定长上下文效果，也不能把这个粗算当成已完成8K/16K实验。

公共后端可以进一步评估QKV与MLP gate/up权重预打包、较少的线性调用，以及更稳定
的执行图。这类修改要同样给予原生/检索基线，记录额外显存、一次准备成本及冷/热
请求；改变Draft数值仍需完整Target核验。不能通过只优化RESCUE的公共算子来认定
注意力方法本身优于更慢的基线。

## 6. 建议的推进顺序

1. 先验证按需探针、静态仿射memo和增量KV：主要是组织方式改变，先保持当前
   参数、选择、长度策略，检查轨迹与吞吐，不将算法改变混入执行收益。
2. 固定k=4做M1/M2开关对照，再检查联合覆盖选取和Teacher Top-K注入的排序是否
   需要统一。当前数据不能给两个模块分摊全部约12ms/轮的差额。
3. 在真实联合rollout上训练/校准注入权重和计算路由，允许少注入或完全跳过。
   以接受收益与成本共同决策，不将软门控的小数值等同于计算节省。
4. 最后在新的注入配置下重训/评估长度收益预测，检验首token后的确认是否值得。
   每次配置选择限于训练/开发集，最终需要独立确认与长上下文评价。

本次分析没有自动启动这四步实验，也没有将候选改动作为已实现功能。
